AIコード時代のレビューに向けて：
「②設計根拠」をどのコード位置に残すべきかの予測

レビューで「なぜこの実装か」と問われた箇所をマイニングし、設計根拠（design rationale）が必要だったのにコードに無かった位置の正解ラベルを構築する。

Modern Code Review Design Rationale AI-authored Code Mining Software Repositories

1. 問題設定

AIエージェントが大量のコードを生成する時代に、人間のコードレビューがボトルネック化する。これは仮説ではなく実測がある。

  • エージェント生成PRの約70%が「レビュー長期化・未レビュー・却下」に陥る。(Hassan et al. 2025, Agentic Software Engineering, arXiv 2509.06216)
  • AIレビューツールを導入しても人間のレビューは速くなっていない（業界調査：29%遅化・24%時短・47%変化なし, LeadDev）

レビューには2つの目的がある——品質保証と知識移転・共同所有。効率化は後者を侵食しうる（理解せず通す rubber-stamping のリスク）。本研究は generic なレビュー効率化ではなく、「変更理解」の核心的な詰まりどころに焦点を絞る。

2. 詰まりどころ＝「なぜこう変更したか（rationale）」

複数の一次文献が、レビューの困難の中心に 変更の rationale（理由） があることを示している。

文献知見
Tao et al. FSE 2012rationale は変更理解で最重要の情報ニーズ。ただし良い変更説明があれば容易。
Ebert et al. SANER'19/EMSE'21missing rationale は最頻の混乱原因の1つ。なのに文献の解決策は実質1つだけ＝最大ギャップ。著者自身が「コード/コメントから rationale を自動抽出する研究をすべき」と提言。
Pascarella et al. CSCW 2018レビュアが最も頻繁に問うのは「代替案は妥当か(N1)」、次いで「正しく理解したか(N2)」、rationale(N3)。N1の判断にも「なぜこの方法を選んだか」が要る。

rationale の3層 — 狙うのは②

① 動機・目的

なぜこの変更が必要か。コミットメッセージで埋まる。生成・評価技術で解決されつつある(Zeng et al. ICSE 2026 の "Why" ＝機能的目的)。

② 設計根拠 ★狙い

なぜこの方法を選んだか／代替案とのトレードオフ。どこにも書かれず、レビューの難所。commit研究の "why" は①であって②ではない。

③ 正当化

正しい・壊れないと言える理由。②と連続。

重要：論文で②を主張する際は「commit message 研究の why（＝①機能的目的）」と明確に区別する必要がある。さもないと「commitのwhyは解決済み」と却下される。この区別自体が貢献の輪郭を鋭くする。

3. 先行研究の空白

「説明をどこに置くか」と「rationale を文書化するか」は別々に研究されてきたが、その交差点が空いている。

系統代表研究限界
A. コメント位置予測
（どこに説明を書くか）		"Where should I comment my code?" (ICSE 2020)／CommtPst (JSS 2020)／COMCAT (2024)位置は当てるが ①動機/②設計根拠を区別しない。レビュー需要を使わず既存コメントを正解にする。
B. rationale の文書化/抽出
（種類）		DRMiner (ASE 2024, issueログから)／AlSafwan & Servant (commit rationale を15要素分解)②を扱うが コード上のどこ(hunk/行)かは当てない。レビューでもない。
C. レビュー説明・質問の分析"Explaining Explanations" (TOSEM 2024)／"Code Review as Decision-Making" (EMSE 2025, 質問の認知モデル)質問を扱うが小規模観察・認知モデルで、位置予測でもマイニングでもない（むしろ需要の裏づけとして引用可）。
D. AIコードレビュー（上位文脈）MSR'26 "Review Effort in AI-Generated PRs"／SWE-PRBench (2026)工数予測・品質ベンチ。rationale の位置は扱わない。
空白＝本研究の位置：「コードのどの hunk/行に②設計根拠を残すべきか」の予測は見当たらない。 系統A（位置）× 系統B（種類＝②）の交差点。差別化点は3つ： (1) レビュー需要を正解ラベル源に使う／(2) ①と②を区別し②に絞る／(3) 位置粒度 × ②種類。

4. 研究の問いとアイデア

RQ（暫定）： コードの hunk/行単位で「ここには②設計根拠を残しておくべき」箇所を予測できるか。それは「レビュアが なぜ と問いがちな箇所」をどれだけ捉えるか。

正解ラベルの作り方 — レビュー質問を必要性の anchor にする

「ここに②が必要だった」という ground truth を、2つの証拠の積で定義する：

  • (a) レビュアが why を聞いた ＝ 第三者が「なぜか分からなかった」独立した需要の証拠。同時に「その rationale がコードに書かれていなかった」証拠（書いてあれば聞かれない）。
  • (b) 作者が弁明し、それが受理された（コードを直さず通った）＝ 実装者のミス修正ではなく本物の設計判断である証拠。

これにより「ミス」と「本物の設計判断」を分離し、laziness 交絡（情報は既にどこかにあった）も排除する。受理された作者の回答＝ground-truth の rationale。

5. データ収集パイプライン

AIコードのレビューは GitHub にしか存在しないため、実証は GH Archive（自前DL・課金なし）。まず人間PRで手法を確立する。収集窓＝2025-03-03〜03-09 の連続1週間。

6. 限界（正直に）

  • Pascarella bias：拾えるのは「声に出された需要」だけ＝高 precision・低 recall。モデルが学ぶのは「客観的に②が必要な箇所」ではなく「レビュアが聞きがちな箇所」。学習正例としては許容だが主張時に断る。
  • Stage 3 の信頼性：positive率がシャード間で 31.5〜53.1% とばらつき大＝LLM間の基準解釈ぶれ。43.1% は粗い推定。現在、人手検証セット（各シャード10件・計100件）で precision を較正中。
  • Stage 2 の弱さ：行不変フィルタは Stage 1 の返信フィルタと情報が重複し、追加弁別はほぼゼロだった。「受理」の強い証拠が merged のみ（isResolved 未取得）。
  • 公開リポジトリ・人間PRのみ（手法確立後にAIコードへ拡大）。

7. 現状と次の一手

データ収集パイプライン（Stage 1–3）は完走し、正例 1,094 件を確保。現在はラベル整備の前段としてアノテーション品質の人手検証を実施している。

  • ① Stage 3 の precision を人手検証で較正（実施中）
  • ② 正例の diff_hunk/original_line を取得し、位置予測の正解ラベルを整備
  • ③ 負例（同一PR内で聞かれなかった hunk 等）の設計 → 位置予測モデルの学習・評価
